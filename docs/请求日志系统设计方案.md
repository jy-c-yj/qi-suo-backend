## 0. 决策一览

| 决策点 | 结论 |
|---|---|
| 异步路线 | RabbitMQ 解耦，生产者 = 切面，消费者 = 独立监听器 |
| 代码位置 | 全部写在 `qi-suo-sys-log`，其他服务引依赖 + 打 `@Log` |
| 数据表 | 共享库 `qi-suo` 中单表 `sys_oper_log` |
| 采集范围 | 仅匹配到 `@Log` 注解的方法 |
| 记录内容 | 元信息 + 请求参数（脱敏后），不含响应体 |
| 消费者归属 | sys-log 内置，**仅 adminService 开开关** |
| 消费失败 | 有限重试 3 次 → 死信队列 |
| 发送失败 | 静默降级，绝不影响业务 |
| 成败判定 | 失败也记，口径 = `Result.code == 1` |
| 表字段 | 精简字段集 |
| 开关 | 配置总开关 + `@Log` 注解双重控制 |
| 非 JSON 请求 | 跳过 multipart/流，其余照记 |
| `@Log` 属性 | `module` + `desc` |
| 落库方式 | 攒批 insert |
| 重复写入 | `message_id` 唯一索引 + `INSERT IGNORE` |
| 数据保留 | 定时删除 30 天前 |
| 查询端 | 不做，只入库 |

## 1. 总体链路

```
┌─ 网关 ──────────────────────────────────────────────┐
│  TraceFilter: 生成/透传 X-Trace-Id → 请求头           │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─ 业务服务 (user/merchant/admin/file/auth) ───────────┐
│  Controller ─◀─ logAop (@Around, 只切 @Log)          │
│      │            │                                   │
│      │            ├─ joinPoint.getArgs() → 脱敏 → JSON│
│      │            ├─ SecurityContext → userId        │
│      │            ├─ 耗时 / HTTP 状态 / Result.code   │
│      │            └─ LogMessageSender.send() ─┐      │
│      ▼                                        │try-catch 包住│
│  业务返回                                      │      │
└───────────────────────────────────────────────┼──────┘
                                                ▼
                     qi-suo.log.exchange (topic)
                            routing-key: log.request
                                                │
                                                ▼
                     qi-suo.log.queue  ◀── x-dead-letter-exchange
                                                │         │
                                                │   (重试 3 次失败)
                                                ▼         ▼
                                   RequestLogConsumer   qi-suo.log.dlx
                                   (@ConditionalOnProperty)  → qi-suo.log.dlq
                                   adminService 独占启动
                                                │
                                          攒批 INSERT IGNORE
                                                ▼
                                     MySQL: qi-suo.sys_oper_log
                                                        ▲
                                     LogCleanTask ──────┘ 每天删 30 天前
```

## 2. `qi-suo-sys-log` 模块结构

```
qi-suo-sys/qi-suo-sys-log/

    ├── dto/RequestLogMessage.java   MQ 消息体
```

> 模块位置：`qi-suo-sys/qi-suo-sys-log`。`qi-suo-sys` 是与 `qi-suo-common` 平级的聚合模块（packaging=pom），后续的运维/后台类模块挂在这里，不再混进 common。

### 包名建议（改名的最后时机）

现在 `com.cyj.Annotation` / `com.cyj.Aop` 是**大写首字母**，不符合 Java 包名约定。`@Log` 目前零使用方，现在改成 `com.cyj.annotation` / `com.cyj.aspect` 是零成本，接入之后就改不动了。**建议顺手改掉。**

### pom 需补的依赖

```xml
spring-rabbit                            <!-- 父 pom 的 dependencyManagement 已有版本 -->
mybatis-plus-spring-boot3-starter
lombok
<!-- 注意：不要引 qi-suo-common-rabbitMQ，会引入重复的 MessageConverter bean -->
```

`spring-boot-starter-aop` 已在，不用动。`jakarta.servlet` 由各服务的 `starter-web` 传递而来。

### 两个"零配置生效"的关键点

**① 组件自动装配不需要 `AutoConfiguration.imports`**

所有服务主类都在 `com.cyj`（`com.cyj.UserServiceApplication` 等），默认 `@ComponentScan` 就是 `com.cyj`，而 sys-log 的类也在 `com.cyj` 下 → `@Aspect` / `@Configuration` / `@Component` **会被自动扫到**，无需任何装配文件。

**② Mapper 自动注册也不需要 `@MapperScan`**

全项目没有一处 `@MapperScan`，Mapper 全靠 `@Mapper` + MyBatis 自动配置扫主类所在包（`com.cyj`）。所以 `SysOperLogMapper` 放在 `com.cyj.mapper` 下，**5 个服务零配置就能扫到**。

> 这两点成立的前提是主类包名是 `com.cyj`。哪天有服务主类挪到更深包，链条会静默断掉 —— 值得在 README 里记一笔。

## 3. `@Log` 注解

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Log {
    String module();        // 业务模块，如 "商品"
    String desc();          // 操作描述，如 "新增商品"
}
```

两个属性都设为**必填**（不给默认值），避免有人漏填导致表里全是空 module。

用法：

```java
@Log(module = "商品", desc = "新增商品")
@PostMapping("/product")
public Result<Void> addProduct(@RequestBody ProductDTO dto) { ... }
```

## 4. 切面实现要点

```java
@Around("@annotation(logAnn)")   // 绑定注解实例，直接读 module/desc
public Object around(ProceedingJoinPoint pjp, Log logAnn) throws Throwable
```

### 骨架

```
long start = System.nanoTime();
Throwable err = null;
Object ret = null;
try {
    ret = pjp.proceed();
    return ret;
} catch (Throwable t) {
    err = t;
    throw t;                  // ★ 必须原样抛出，绝不吞业务异常
} finally {
    try { 组装消息 + 发送 } catch (Exception e) { log.error(...) }   // ★ 静默降级
}
```

### 三个关键取舍

**① 请求参数用 `pjp.getArgs()`，不用 `ContentCachingRequestWrapper`**

读 body 的经典做法要在 Filter 里提前包装 request，切面再从缓存里取 —— 因为切面执行时 Spring 已经把 body 读走了，直接在切面里包装只会拿到空缓存。这套东西的代价是：multipart 文件流会被吃掉、编码问题、GET/表单要单独处理。

**用 `pjp.getArgs()` 直接拿已反序列化的方法入参**，这些问题全部不存在，而且天然满足"跳过 multipart/流"—— 因为 `MultipartFile` 只是一个参数类型，过滤掉即可。

需要过滤的参数类型：`HttpServletRequest`、`HttpServletResponse`、`MultipartFile`、`InputStream`、`OutputStream`、`HttpSession`、`BindingResult`、`Model`。剩余参数 Jackson 序列化 → 脱敏。

**② 用户 id 从 `SecurityContext` 取，要做好空值容错**

`AuthFilter` 的逻辑是：拿不到 `Auth-claims` 头就**直接放行**，此时 `SecurityContextHolder` 里是空的或 anonymous。所以：

```java
Authentication auth = SecurityContextHolder.getContext().getAuthentication();
userId = (auth != null && auth.getPrincipal() instanceof Number)
       ? ((Number) auth.getPrincipal()).longValue()
       : -1L;
```

表里 `user_id` 默认 `-1` 表示"未登录/取不到"。

**③ 成败判定看 `Result.code`，不要看 `data` / `msg`**

`Result.success(String)` 这个重载会把值塞进 **`msg`** 而不是 `data`（见 `Result.java:31-36`）—— 项目里已有这个坑，判定时只认 `code`。

```
if (err != null)                success = 0, bizCode = 0, errorType/Msg = 异常信息
else if (ret instanceof Result) success = (code == 1 ? 1 : 0), bizCode = code
else                            success = 1, bizCode = 1
```

### 其他取值

| 字段 | 取法 |
|---|---|
| `uri` | `request.getRequestURI()` |
| `http_method` | `request.getMethod()` |
| `client_ip` | `X-Forwarded-For` 第一段 → 退化到 `X-Real-IP` → 退化到 `remoteAddr`（经网关后 `remoteAddr` 是网关地址，**必须优先取 XFF**） |
| `http_status` | `response.getStatus()`（从 `RequestContextHolder` 取） |
| `cost_ms` | `(System.nanoTime() - start) / 1_000_000` |
| `trace_id` | `X-Trace-Id` 头，取不到则本地生成 32 位 UUID 兜底 |
| `service_name` | `${spring.application.name}` 注入 |

## 5. MQ 拓扑与消息体

### 拓扑声明（`RabbitLogConfig`）

| 名称 | 类型 | 说明 |
|---|---|---|
| `qi-suo.log.exchange` | topic, durable | 主交换机 |
| `qi-suo.log.queue` | durable | 主队列，`x-dead-letter-exchange = qi-suo.log.dlx`、`x-dead-letter-routing-key = log.dead` |
| routing key | `log.request` | 单队列单消费者，服务名放消息体，不需要按服务分路由键 |
| `qi-suo.log.dlx` | direct, durable | 死信交换机 |
| `qi-suo.log.dlq` | durable | 死信队列，绑 `log.dead` |

消息以 `PERSISTENT` 投递。消费者 `concurrency = 1`、`prefetch = 20`（配合攒批）。

`MessageConverter` 声明时**必须加 `@ConditionalOnMissingBean`**，否则若某服务同时引了 `common-rabbitMQ`，两个 `Jackson2JsonMessageConverter` bean 会冲突。

### 消息体 `RequestLogMessage`

```json
{
  "messageId":  "8f3a...（UUID 36 位）",
  "traceId":    "a1b2c3...（32 位）",
  "serviceName":"qi-suo-user",
  "module":     "商品",
  "operation":  "新增商品",
  "uri":        "/merchant/product",
  "httpMethod": "POST",
  "clientIp":   "192.168.1.5",
  "userId":     1001,
  "requestParam": "{\"name\":\"手机\",\"password\":\"***\"}",
  "costMs":     37,
  "httpStatus": 200,
  "bizCode":    1,
  "success":    1,
  "errorType":  "com.cyj.exception.ProductIsNotExistException",
  "errorMsg":   "商品不存在",
  "createTime": "2026-10-15 10:00:00.123"
}
```

`requestParam` 在发送前截断到 **4096 字符**（可配），超出追加 `...truncated`，保证单条消息不超过约 5KB。

## 6. 消费者 `RequestLogConsumer`

```java
@ConditionalOnProperty(prefix = "qi-suo.log", name = "consumer-enabled", havingValue = "true")
```

**只有 adminService 把 `consumer-enabled` 设成 `true`**，其余服务连这个 bean 都不注册，零开销。

### 攒批 + 手动 ack 的语义

```
收到消息 → 塞进本地 List 缓冲
  ├─ 缓冲 >= batch-size(100)                    → flush
  └─ 缓冲未满但距上次 flush > flush-interval-ms → flush

flush: mapper.batchInsertIgnore(list) 成功 → basicAck 整批
                                    失败 → basicNack(requeue=false) 整批
                                          → DLX → DLQ
```

**这里有个必须讲清楚的交互**：批量写失败时整批 nack，但批里可能已有部分成功写入 —— 重试后就会重复。这正是 `message_id` 唯一索引存在的原因：`INSERT IGNORE` 让重复写入静默变成 no-op。

`batchInsertIgnore` 需要手写 SQL（MP 的 `saveBatch` 不支持 `IGNORE`）：

```sql
INSERT IGNORE INTO sys_oper_log (message_id, trace_id, ...) VALUES
  (...), (...), (...);
```

### 定时 flush 的坑

"攒够 100 条或满 1 秒"里的后半句需要一个 `@Scheduled` 心跳去查看缓冲。低流量时（比如夜里）如果只靠"攒够 100 条"，日志会一直压在内存里不落库。这个心跳不能漏。

## 7. 数据库表设计

### DDL

```sql
CREATE TABLE `sys_oper_log` (
  `id`            BIGINT UNSIGNED   NOT NULL AUTO_INCREMENT          COMMENT '主键',
  `message_id`    CHAR(36)          NOT NULL DEFAULT ''              COMMENT 'MQ 消息 id，幂等去重用',
  `trace_id`      CHAR(32)          NOT NULL DEFAULT ''              COMMENT '全局链路 id，网关生成',
  `service_name`  VARCHAR(32)       NOT NULL DEFAULT ''              COMMENT '来源服务，如 qi-suo-user',
  `module`        VARCHAR(64)       NOT NULL DEFAULT ''              COMMENT '@Log(module)',
  `operation`     VARCHAR(128)      NOT NULL DEFAULT ''              COMMENT '@Log(desc)',
  `uri`           VARCHAR(255)      NOT NULL DEFAULT ''              COMMENT '请求路径',
  `http_method`   VARCHAR(10)       NOT NULL DEFAULT ''              COMMENT 'GET/POST/PUT/DELETE',
  `client_ip`     VARCHAR(64)       NOT NULL DEFAULT ''              COMMENT '客户端 ip（XFF 首段）',
  `user_id`       BIGINT            NOT NULL DEFAULT -1              COMMENT '用户 id，-1 表未登录/取不到',
  `request_param` TEXT                                               COMMENT '脱敏后的请求参数 json，截断 4096 字符',
  `cost_ms`       INT UNSIGNED      NOT NULL DEFAULT 0               COMMENT '耗时毫秒',
  `http_status`   SMALLINT UNSIGNED NOT NULL DEFAULT 0               COMMENT 'HTTP 状态码',
  `biz_code`      INT               NOT NULL DEFAULT 0               COMMENT 'Result.code，1 成功 0 失败',
  `success`       TINYINT(1)        NOT NULL DEFAULT 1               COMMENT '1 成功 0 失败',
  `error_type`    VARCHAR(255)      NOT NULL DEFAULT ''              COMMENT '异常类全限定名',
  `error_msg`     VARCHAR(1024)     NOT NULL DEFAULT ''              COMMENT '异常消息 / 业务失败信息',
  `create_time`   DATETIME(3)       NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '请求发生时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_message_id` (`message_id`),
  KEY `idx_trace_id`    (`trace_id`),
  KEY `idx_create_time` (`create_time`),
  KEY `idx_user_time`   (`user_id`, `create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci
  COMMENT='接口请求日志';
```

### 字段说明与取舍理由

| 字段 | 为什么这么设计 |
|---|---|
| `message_id` CHAR(36) | UUID 带横线固定 36 位，**唯一索引的用途是幂等而非业务**。用 `CHAR` 而非 `VARCHAR`，定长索引效率更好 |
| `trace_id` CHAR(32) | 32 位无横线 UUID，定长 |
| `user_id` 默认 `-1` | 用 `NOT NULL DEFAULT -1` 而非 `NULL`：未登录是常态，`-1` 可直接参与索引和比较，不用处理 `NULL` 三值逻辑 |
| `request_param` TEXT | 选择 `TEXT` 而不是 `VARCHAR(4096)`：utf8mb4 下 `VARCHAR(4096)` 最坏占 16KB，和其余 varchar 相加会逼近 InnoDB 单行 65535 字节上限。用 `TEXT` + 应用层截断 4096 字符更稳 |
| `cost_ms` INT UNSIGNED | 无符号，天然表达"耗时非负" |
| `success` TINYINT(1) | 冗余 `biz_code`，让"成功/失败"这种最高频的筛选条件走最简单的比较 |
| `error_type` / `error_msg` | **不存堆栈全文**。堆栈去应用日志看，两边靠 `trace_id` 对上 |
| `create_time` DATETIME(3) | 毫秒精度，`@Log` 方法可能极快，秒级精度分不出先后 |
| 无 `deleted` / `update_time` | 日志是纯追加，永不变更，不需要逻辑删除和更新时间 |

### 索引设计

只有 4 个索引，全部有明确用途，不做投机性索引：

| 索引 | 用途 |
|---|---|
| `uk_message_id` | **幂等去重**，`INSERT IGNORE` 的依托。必需 |
| `idx_create_time` | **清理任务必需** —— 每天 `DELETE ... WHERE create_time < ...` 要走这个索引，否则全表扫 |
| `idx_trace_id` | 链路查询。等值查找，选择性好 |
| `idx_user_time` | 联合索引，"某用户某时间段的操作"是最典型的排查场景 |

**没建 `idx_uri_time`**：现在不做查询端，URI 维度的索引先不加 —— 索引是写入成本，等真有查询需求、知道实际 SQL 长什么样再补，比现在猜着建更划算。

### 容量估算

假设日均 10 万次请求、平均每条 800 字节：

```
100,000 × 0.8KB ≈ 80 MB/天  →  30 天 ≈ 2.4 GB
```

这个量级 `DELETE` 清理完全可行。**如果日均涨到百万级**（约 24GB / 30 天），就该切换到按月 RANGE 分区 + `DROP PARTITION`，那时再迁移不迟。

## 8. traceId 全链路方案

这是唯一需要**改网关**的部分。网关目前只有 `JwtFilter` / `CorsConfig`，没有全局过滤器。

### ① 网关侧：新增 `TraceFilter implements GlobalFilter, Ordered`

- `getOrder()` 返回比 `JwtFilter` **更小**的值（如 `-100`），保证最先执行
- 读 `X-Trace-Id` 头；没有就生成 32 位 UUID（去掉横线）
- **写回 request header**（这样下游服务能拿到）
- 同时写入 response header，方便前端/浏览器排查时直接看到

### ② 服务侧：切面从 header 取

取不到时本地生成一个兜底，保证绕过网关直连服务调试时也有值。

### ③ Feign 透传（最关键，容易漏）

`user` 调 `merchant` 时，如果不在 Feign 请求里带上 `X-Trace-Id`，**链路会在服务边界断掉**。需要一个 `RequestInterceptor`：

```java
template.header("X-Trace-Id", currentTraceId());
```

放在 sys-log（或 common-feign）里，靠 `com.cyj` 包扫描自动生效。

### ④ 顺带把 traceId 灌进 MDC（强烈建议）

```java
MDC.put("traceId", traceId);
```

这样 Logback 的日志 pattern 里加上 `%X{traceId}` 后，**应用日志的每一行都带 traceId**。排查时从表里拿到 `trace_id`，直接去应用日志里 grep，两边就是同一条链路。这是整个方案里性价比最高的一步 —— 几乎零成本，但把数据库表和文件日志打通了。

> 注意：切面里 `MDC.put` 之后要在 `finally` 里 `MDC.remove`，否则线程池复用会串号。

## 9. 脱敏方案（字段名黑名单）

`SensitiveUtil.mask(Object)` 的算法：

```
递归遍历序列化后的 JSON 树
  ├─ 对象：key 名（忽略大小写）命中黑名单 → 值替换为 "***"
  ├─ 数组：对每个元素递归
  └─ 基本类型：原样保留
```

黑名单（可配）：

```
password, passwd, pwd, oldPassword, newPassword,
token, accessToken, refreshToken, secret, appSecret,
idCard, idcard, certNo, bankCard, cvv,
phone, mobile, telephone
```

**实现要点**：不要做字符串正则替换（`"password":"123"` 这种模式在嵌套/转义时容易误伤或漏网），**在 JSON 树层面按 key 操作**。所以顺序是：

```
getArgs() → Jackson 转 JsonNode → 遍历打码 → 再 toString()
```

**这个方案的两个已知盲区**（选择它时就接受的代价）：

1. 业务自创的字段名（如 `cred`、某个没进黑名单的 `certNo`）会漏网
2. 手机号 / 身份证写在普通命名的字段里（如 `remark: "13800138000"`）抓不到 —— 纯 key 匹配不做值识别

黑名单必须**配置化**，不能硬编码。漏了一个字段时，改配置重启就能补，不用发版。

## 10. 清理任务 `LogCleanTask`

```java
@Scheduled(cron = "0 30 3 * * ?")     // 每天 03:30
@ConditionalOnProperty(prefix = "qi-suo.log", name = "consumer-enabled", havingValue = "true")
```

跟消费者同条件：**只有 adminService 跑清理**，避免 5 个服务同时 DELETE。

分批删除，避免长事务和锁等待：

```sql
DELETE FROM sys_oper_log WHERE create_time < DATE_SUB(NOW(), INTERVAL 30 DAY) LIMIT 1000;
-- 循环执行，直到影响行数 < 1000
```

每批之间 sleep 几十毫秒，给主从复制和 IO 留口气。

> `retention-days` 配成 30。`LIMIT 1000` 分批 + `idx_create_time`，即使 2.4GB 的表也不会造成明显锁表。


MQ 连接配置复用现有 `application-mq.yml` 的写法（`127.0.0.1:5672`，vhost `cyj`），交换机 / 队列名走 `RabbitLogConfig` 里的常量或配置项。

## 12. 各服务接入步骤

以 userService 为例（4 步）：

**① pom 加依赖**

```xml
<dependency>
    <groupId>com.cyj</groupId>
    <artifactId>qi-suo-sys-log</artifactId>
    <version>1.0-SNAPSHOT</version>
</dependency>
```

**② 补 MQ 配置**

`application-mq.yml` 已存在（host / vhost / 账号都有），只需在 `application.yml` 的 `profiles.include` 里加上 `mq`。

**③ 打注解**

```java
@Log(module = "购物车", desc = "加入购物车")
@PostMapping("/cart/add")
public Result<Void> addCart(...) { ... }
```

**④ 什么都不用配** —— 切面、Mapper、Feign 拦截器都靠 `com.cyj` 包扫描自动生效。

### 各服务的差异

| 服务 | 现状 | 需要做的 |
|---|---|---|
| **admin** | 有 `application-mybatis.yml`，**无 mq profile** | 新建 `application-mq.yml` + profile include + **`consumer-enabled: true`** |
| **user** | `application-mq.yml` 已有 | 加 sys-log 依赖 + profile include |
| **merchant** | `application-mq.yml` 已有 | 同上 |
| **file** | 无 mq 配置 | 新建 `application-mq.yml` + profile include |
| **auth** | 无 mq 配置 | 新建 `application-mq.yml` + profile include |

> user / merchant 的 pom 里 `qi-suo-common-rabbitMQ` 依赖是**注释掉的**。sys-log 自带 `spring-rabbit`，**不要**因为这个方案把它放开 —— 两个 `MessageConverter` bean 会撞车。

## 13. 落地里程碑

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **M1** | 建表 + sys-log 全部代码 + admin 打注解 | 调 admin 一个接口，`sys_oper_log` 里出现一条记录 |
| **M2** | 网关 TraceFilter + Feign 拦截器 + MDC | 一次跨服务调用产生多条记录，`trace_id` 相同；应用日志能 grep 到 |
| **M3** | user / merchant / file / auth 接入 | 5 个服务的记录都进同一张表 |
| **M4** | 压测攒批 + 死信验证 + 清理任务上线 | 手动灌坏消息进 DLQ；改 `retention-days=1` 验证清理生效 |

**M1 让 admin 既当生产者又当消费者**，一个服务就能端到端验证整条链路，不用同时起 5 个服务 —— 这是把消费者放在 admin 的一个额外好处。

## 14. 风险与坑清单

按"踩了会很难查"排序：

1. **`Result.success(String)` 把值塞进 `msg`**（`Result.java:31`）—— 判成败只认 `code`，别碰 `data` / `msg`。
2. **异常必须原样抛出**。切面里的 `catch` 只准记录，不准吞、不准包装成别的异常。
3. **发送消息必须独立 try-catch**。业务已成功、MQ 挂了，接口不能跟着失败。
4. **攒批 + 整批 nack 会产生重复**，必须靠 `uk_message_id` + `INSERT IGNORE` 兜底 —— 这两件事是绑定的，少一个就会写出重复数据。
5. **攒批的定时 flush 不能漏**。低流量时段只靠"攒够 100 条"会让日志压内存不落库。
6. **切面里不要碰 `ContentCachingRequestWrapper`**。用 `getArgs()`，否则 multipart 文件流被吃、body 读空。
7. **`MessageConverter` 加 `@ConditionalOnMissingBean`**，否则和 `common-rabbitMQ` 冲突。
8. **IP 必须优先取 `X-Forwarded-For`**。经网关后 `remoteAddr` 是网关的地址。
9. **`MDC.remove` 不能忘**。线程池复用会串 traceId。
10. **Feign 拦截器漏了 = 链路断**。跨服务 trace 依赖它，容易在 M1 阶段"看起来正常"而漏掉。
11. **admin 是单点消费者**。admin 停机期间消息堆在队列里，恢复后继续消费 —— 不丢，但日志有延迟。队列没有设 TTL / 最大长度，不会自动丢弃。
12. **`@Log` 方法被同类内部调用（`this.xxx()`）不走代理**，切面失效。这是 Spring AOP 的通用限制，接入时要注意调用方式。
13. **包名 `com.cyj.Annotation` / `com.cyj.Aop` 大写**，改名的最后时机是现在。
14. **主类必须在 `com.cyj`**。切面和 Mapper 的"零配置生效"完全依赖这一点，有服务挪包就会静默失效。

## 15. 预设默认值（可推翻）

这几个没在需求确认阶段明说，按惯例预设，不合适随时改：

| 项 | 取值 | 理由 |
|---|---|---|
| 表名 | `sys_oper_log` | 后台日志表的通行命名 |
| 交换机 / 队列名 | `qi-suo.log.exchange` / `.queue` / `.dlx` / `.dlq` | 与 `spring.application.name` 前缀风格一致 |
| 参数截断 | 4096 字符 | 消息体控制在 5KB 内 |
| 攒批 | 100 条 / 1000ms | 常见起点，M4 压测再调 |
| 清理时间 | 每天 03:30 | 低峰期 |
| 批次 | 1000 行 / 批 | 兼顾删除速度和锁等待 |
| traceId 头名 | `X-Trace-Id` | 事实标准 |
| 参数过滤方式 | 白名单外过滤，而非 blacklist | 新增容器类型参数时不会意外被序列化 |
